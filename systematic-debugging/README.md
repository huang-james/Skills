# systematic-debugging · 系统化调试

> 遇到**任何 bug、测试失败、异常行为**时，在提出修复之前调用。
> 工作流是强制的：**先定位根因 → 提出修复方案 → 等用户明确批准 → 才改代码。**

## 解决什么问题

最常见的调试失败模式不是"不会修"，而是**没找到根因就开始改**：猜一个改一下、同时改好几处、修完症状根因还在、越修越乱。这个技能用流程把"瞎猜"堵死——**症状修补即失败**。

## 两条铁律

```
1. 没有根因调查，不得提出修复
2. 修复方案未经用户明确批准，不得改动任何代码
```

Phase 1–3 中的诊断实验（临时日志、复现脚本）是允许的，但交付修复方案前必须撤销。

## 四个阶段（必须按序完成）

| 阶段 | 关键动作 | 通过标准 |
|------|---------|---------|
| **1. 根因调查** | 仔细读错误信息；稳定复现；检查最近改动；多组件系统在每层边界加诊断日志收集证据；沿调用栈反向追踪坏值的源头 | 明白 WHAT 和 WHY |
| **2. 模式分析** | 找同代码库里能正常工作的相似代码；完整阅读参考实现；逐项列出工作版与损坏版的差异 | 找到差异 |
| **3. 假设与验证** | 明确写下单一假设；用**最小的诊断性改动**验证（一次只动一个变量）；不奏效就换新假设，不叠加修改 | 假设被证实 |
| **3.5. 批准门（强制）** | 按固定结构呈现：根因（带 `file:line` 证据）→ 证据 → 修复方案 → 备选方案 → 验证计划；然后**结束回合停下等待** | 用户明确批准 |
| **4. 实施** | 先写失败测试（红→绿）；只修根因，一次一个改动，不夹带重构；跑全量测试确认 | bug 解决，测试全过 |

## 3 次修复失败 = 架构问题

每次修复都在不同地方暴露新问题、修复需要"大规模重构"才能落地、每次修复制造新症状——这时停下来质疑根本：这个模式本身是否成立？是惯性让我们死守它吗？**与人类搭档讨论后再动手，第 4 次盲修被禁止。**

## 危险信号（出现即回到 Phase 1）

- "先快速修一下，以后再调查"
- "改改 X 试试看"
- 一次改多处再跑测试
- "很可能是 X，先修了"
- 在提出修复方案的同回合就开始改代码
- 已经失败 2 次以上还想着"再试一次"

## 配套技术（同目录文档）

- **[root-cause-tracing.md](./root-cause-tracing.md)** — 沿调用栈反向追踪，找到坏值的最初源头，在源头修复而非症状处
- **[defense-in-depth.md](./defense-in-depth.md)** — 找到根因后，在多个层次加校验防止同类问题
- **[condition-based-waiting.md](./condition-based-waiting.md)** — 用条件轮询替代任意超时，消灭时序类 flaky 测试

## 使用方式

安装后由智能体在任何调试场景自动调用（配合全局规则），或手动 `/systematic-debugging` 触发。

## 安装

```bash
# ZCode
cp -r systematic-debugging ~/.zcode/skills/

# Claude Code
cp -r systematic-debugging ~/.claude/skills/
```
