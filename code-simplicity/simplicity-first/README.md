# simplicity-first · 简洁第一原则

> 一道面向**所有代码**的简洁性门槛：在编写、修改任何代码之前，以及审查任何 diff 之前调用。
> 它把"过于复杂、体量过大的代码"当作**正确性 bug**，而不是风格问题。

## 解决什么问题

AI 编码助手最常见的问题不是写不出代码，而是**写太多代码**：为了一个小修复引入新的类、新的配置项、新的返回结构；为了"通用性"加一层永远不会被第二个人调用的抽象。这个技能在动手之前先立规矩：**先找最小的修复，再写代码。**

## 核心理念

**人类可读性第一，智能体可追溯性是底线。**

- 人应该一遍就能读懂代码——读不懂的代码就是 bug，无论它多"聪明"
- 智能体至少要能从入口点追到执行分支、数据、输出和测试，不需要还原隐藏的控制流

## 五条硬规则

| # | 规则 | 一句话解释 |
|---|------|-----------|
| 1 | 人读不顺的代码是 bug | 一遍读不完的函数，重构或删除；嵌套、间接、炫技都计入正确性 |
| 2 | 冗余代码是 bug | 用最少且可读的行数解决问题；一句话能说清的问题，修复却加了 20+ 行就有嫌疑 |
| 3 | 简洁是核心工程指标 | 两个都能用的设计，选代码更少、概念更少、文件更少的那个；不为"未来"加配置和字段 |
| 4 | 禁止过度封装 | 单一调用点不建新类/辅助函数/模块；辅助函数需要 3+ 真实调用点且逻辑非平凡，否则内联 |
| 5 | 简洁 ≠ 删功能 | 功能、性能开关、可观测性是有意设计，不借"简化"之名移除；简化实现，保留行为面 |

## 收工前检查清单

- [ ] 人冷读一遍能懂吗？（这是门槛）
- [ ] 这个 diff 能再小一半吗？拿不准就改小
- [ ] 有新类/新文件？3+ 调用点才配存在，否则删
- [ ] 改了签名/返回结构？确认每个调用方都真的需要
- [ ] 注释只写"为什么"，2–4 行以内，写给外部读者看
- [ ] 一个问题 = 一个最小 diff，不夹带无关"改进"
- [ ] 真实使用中触发不了的"bug"不值得修

## 使用方式

安装后由智能体在**每次代码变更前**自动调用（配合全局规则），或手动 `/simplicity-first` 触发。

## 安装

```bash
# ZCode
cp -r code-simplicity/simplicity-first ~/.zcode/skills/

# Claude Code
cp -r code-simplicity/simplicity-first ~/.claude/skills/
```
